Прокидывает порты P2P-камеры Dahua (по серийнику) на localhost через облачный протокол DH «Dahua HTTP P2P». По сути — замена оригинального Python-скрипта, но на Go и с полной совместимостью по CLI.

Зависимость всего одна — `golang.org/x/crypto`.

## Что умеет

- **Один туннель** или **мультипорт** — можно прокинуть сразу несколько портов камеры на разные локальные порты, через параллельные PTCP-каналы (по умолчанию их 3).
- **Пробивает NAT** (инвертированный STUN), а если камера не откликнулась — автоматически уходит в релей.
- **Проверяет камеру перед стартом** мультипорт-режима: если серийник мёртвый или не существует (`404`), сразу об этом сообщает, без лишних попыток.
- **Сам ретраит** упавший туннель (3 попытки), а порты, которые так и не поднялись, помечает `[FAIL]` и спрашивает — ретраить их или закрыть всё.
- **Диссектор пакетов** (`--decode`) — разбирает пойманные пакеты офлайн (DH HTTP, инвертированный STUN, PTCP).
- Держит соединение живым: **heartbeat** по PTCP раз в 5 секунд и **RTSP keepalive** (`OPTIONS * RTSP/1.0`) для простаивающих клиентов (раз в 25 секунд).
- Серийник можно писать хоть до флагов, хоть после — как в оригинальном скрипте.

## Сборка

Нужен Go 1.22+ (более новые тоже подойдут).

```sh
go build -o godh .
# тесты
go test ./...
# статический анализ
go vet ./...
```

## Как пользоваться

```
godh [options] <serial>
```

Серийник можно поставить перед флагами — программа сама перенесёт его в конец:

```sh
./godh 4E0743BPAGFE388 -p 5080,5081:80,81
```

### Флаги

| Флаг | Короткий | Что делает |
|------|----------|----------|
| `--debug` | `-d` | подробный отладочный вывод протокола (запросы, STUN-пакеты, PTCP-фреймы) |
| `--log-retries` | `-lr` | лог ретраев с таймстемпами |
| `--type` | `-t` | тип устройства: `0` — без авторизации (по умолчанию), `1` — с авторизацией |
| `--username` | `-u` | логин (для `--type 1`) |
| `--password` | `-P` | пароль (для `--type 1`) |
| `--randsalt` | `-s` | RandSalt из info-блоба (для `--type 1`) |
| `--port` | `-p` | список портов, см. ниже |
| `--threads` | `-mt` | сколько параллельных туннелей поднимать (по умолчанию 3) |
| `--decode` | `-D` | режим диссектора |
| `--decode-type` | `-T` | что декодировать: `auto`, `dhttp`, `istun`, `ptcp` (по умолчанию `auto`) |

`--help`/`-h` выводит сгруппированную справку с примерами.

### Как задавать порты (`--port`)

- `-p 5080,5081,5082:80,81,82` — явные пары «локальный:камерный», один к одному;
- `-p 8080,8081,8082:80` — несколько локальных портов на один камерный;
- `-p 80-85` — только камерные порты, локальные подбираются случайно;
- `0:81` — локальный порт `0` означает «любой свободный»;
- диапазоны тоже работают: `-p 8080-8082:80-82`;
- если `--port` не указан — открывается один туннель `554:554` (RTSP).

Локальные порты слушаются на `0.0.0.0`, камера отдаёт видео на `127.0.0.1:<local>`.

### Режимы работы

**Single** — один порт, без интерфейса, просто вывод в stdout:
```sh
./godh 4E0743BPAGFE388 -p 5080:80
```

**Multi** — включается дашборд со статусом портов. Срабатывает автоматически, если портов несколько, или если явно указан `-mt`:
```sh
./godh 4E0743BPAGFE388 -p 5080,5081:80,81 -mt 4
```
```
Opening 2 ports on 4E0743BPAGFE388 | Threads: 3
[..] Opening 4E0743BPAGFE388:80 | Connecting...
[OK] Obtained 4E0743BPAGFE388:80 -> 127.0.0.1:5080
[OK] Obtained 4E0743BPAGFE388:81 -> 127.0.0.1:5081
Obtained 2 ports on 4E0743BPAGFE388:80,81 | localhost:5080,5081
```

**Decode** — разбирает пойманный пакет без подключения к камере:
```sh
./godh -D -T ptcp <hex>
./godh -D -T auto 0x... 0x...
echo '<hex>' | ./godh -D
```

### Что будет при ошибках

- **Серийник не существует или камера выключена** (`404`) — ретраев не будет, просто одна строка:
  ```
  4E0743BPAGFE389 isn't exist or turned off.
  ```
- **Камера требует авторизацию** (`403`) — добавьте `-t 1 -u <user> -P <pass>`:
  ```sh
  ./godh <sn> -t 1 -u <user> -P <pass> -p ...
  ```
- **Часть портов не поднялась** — после исчерпания ретраев такие порты помечаются `[FAIL]`, и утилита спрашивает: ретраить (`r`) или закрыть всё (`c`).

## Как это устроено внутри

DH P2P — облачный протокол Dahua: камера держит постоянное UDP-соединение с облаком, а клиент через это облако узнаёт, как до неё добраться. GoDH проходит весь путь целиком: discovery → relay-сессия → регистрация канала → попытка пробить NAT напрямую → либо прямое соединение, либо релей → и наконец туннелирование портов.

### 1. Discovery

Всё начинается с регистратора `www.easy4ipcloud.com:8800`:

- `DHGET /probe/p2psrv` — проверяем, что облако вообще живо;
- `DHGET /online/p2psrv/<sn>` — ищем P2P-сервер, к которому «прицеплена» камера (адрес приходит в `body/US`);
- на найденном сервере — `DHGET /probe/device/<sn>` и `DHGET /info/device/<sn>` (в info-блобе среди прочего лежит RandSalt, который при авторизации передаётся через `-s`).

### 2. Relay-сессия (поднимается всегда)

Даже если в итоге получится соединиться напрямую, relay-сессию всё равно поднимают первой — она даёт учётные данные для PTCP:

- `DHGET /online/relay` — узнаём адрес релейного агента;
- `DHPOST /relay/agent` — получаем `Token` и `Agent`;
- `DHPOST /relay/start/<token>` на агенте — открывается PTCP-сессия;
- обмен токеном `0x17`: клиент шлёт `0x17`, агент отвечает телом, из которого достаётся **sign token** — своего рода пропуск, который потом пригодится при прямом PTCP-хендшейке (`0x19`).

### 3. Регистрация канала

`DHPOST /device/<sn>/p2p-channel` на главном сервере с телом:

```
<body><Identify><aid1> <aid2> ... </Identify><IpEncrpt>true</IpEncrpt>
<LocalAddr>127.0.0.1:<lport></LocalAddr><version>5.0.0</version></body>
```

- `Identify` — случайные 8 байт (AID), от них же считается `invAid = ^AID` для STUN;
- для `--type 1` вместо `<IpEncrpt>` идёт `<IpEncrptV2>` с зашифрованным AES `LocalAddr` и авторизационным блоком (`get_auth`). Ключ выводится через `get_key`/`get_enc` (детали ниже);
- в ответе приходят `LocalAddr` (адрес камеры внутри её NAT), `PubAddr` (публичный адрес), а для type 1 ещё и `Nonce` для расшифровки.

Заодно камера узнаёт адрес клиента и начинает слать ему STUN-инициацию — даже если в итоге всё скатится в релей.

### 4. Пробивание NAT (инвертированный STUN)

Фишка Dahua — весь STUN-пакет побитово инвертирован (`^b`):

- клиент отправляет STUN-инициацию с магией `FF FE FF E7`, cookie, transaction ID, собственным инвертированным адресом (`eaddr`) и `invAid` — сразу и на `LocalAddr`, и на `PubAddr` камеры;
- инициация переотправляется до 2 раз, окно ожидания — 10 секунд;
- если камера сама прислала встречный STUN-init (`FF FE FF E7`) — клиент отвечает `FE FE FF E7` с теми же cookie и transaction ID (два NAT-хоста как бы «жмут руки» через своих провайдеров);
- в ответ на `FE FE FF E7` клиент шлёт подтверждение `FE FE FF F3` (5 раз), дочищает хвосты и переходит к прямому PTCP-хендшейку.

**Если не получилось:** нет ответа за 10 секунд — прямое соединение невозможно. К этому моменту relay-сессия уже готова, камера получила адрес агента через `DHPOST /device/<sn>/relay-channel`, и весь трафик просто идёт через `mainRemote` — тот же облачный релей. Канал при этом работает без проблем, просто не напрямую.

### 5. PTCP-авторизация

PTCP («Phony TCP») — что-то вроде TCP поверх UDP:

- `00 03 01 00` — sync, в ответ ожидается то же самое;
- `0x19` + sign token с шага 2 — передаём «пропуск», ждём `0x1A`;
- `0x1B` — финальный аккорд, ожидается пустое тело.

После этого канал считается авторизованным, и обе стороны переходят к обмену данными.

### 6. Работа канала: реалмы, bind, heartbeat

Несколько портов мультиплексируются внутри одного канала через **реалмы** — 32-битные ID соединений:

- на каждое новое локальное TCP-подключение генерируется `realmID`; клиент сразу регистрируется (чтобы не потерять ранние данные от камеры), а затем отправляется `0x11 BIND` с реалмом и нужным портом камеры;
- камера подтверждает bind ответом `0x12 STATUS` (таймаут — 10 секунд; неудачный bind убивает только это подключение, весь канал остаётся живым);
- данные заворачиваются в `PTCPPayload` (реалм + байты) и уходят как `0x10 DATA`; трафик от камеры маршрутизируется обратно по тому же реалму;
- при разрыве клиента уходит `0x12` с тегом `DISC`;
- **heartbeat**: раз в 5 секунд — пустой фрейм на релей и `0x13 HEARTBEAT` на основной сокет; если основной сокет молчит больше 10 секунд, туннель считается упавшим (и запускаются ретраи);
- **RTSP keepalive**: если клиент простаивает больше 25 секунд, ему шлют `OPTIONS * RTSP/1.0` — иначе DVR-камеры сами рвут соединение по таймауту.

### Криптография для авторизации (type 1)

1. **`get_key`** — `MD5("<user>:Login to <salt>:<pass>")`, результат в верхнем регистре hex. Salt берётся либо из `--randsalt`, либо встроенный `RANDSALT`.
2. **`get_enc`/`get_dec`** — `PBKDF2-HMAC-SHA256(key, nonce, 20000 итераций, 32 байта)` → `AES-OFB` с IV `2z52*lk9o6HRyJrf` → base64. Этим шифруется `LocalAddr` и расшифровывается ответ камеры.
3. **`get_auth`** — `HMAC-SHA256(key)` над строкой `"<nonce><unix-date><payload>"` → base64, оборачивается в XML (`<CreateDate><DevAuth><Nonce><RandSalt><UserName>`).

Для неавторизованных запросов (`--type 0`) и тело, и адрес идут открытым текстом.

### DH HTTP-over-UDP

Все облачные запросы — это обычный HTTP/1.1 поверх UDP, с методами `DHGET`/`DHPOST`:

```
DHPOST /device/4E0743BPAGFE388/p2p-channel HTTP/1.1
CSeq: 1
Authorization: WSSE profile="UsernameToken"
X-WSSE: UsernameToken Username="<user>", PasswordDigest="<sha1-base64>", Nonce="<n>", Created="<date>"

<body>...
```

WSSE-digest считается как `SHA1` от `<nonce><date>DHP2P:<USERNAME>:<USERKEY>`, потом base64. Учётные данные (USERNAME/USERKEY) зашиты прямо в код — это общий клиент облака DH.

### Заголовок PTCP-фрейма

24 байта:

| Байты | Поле | Что означает |
|----------|------|-------|
| `0:4` | magic | `PTCP` |
| `4:8` | `Rlid` | сколько байт отправил пир (ack) |
| `8:12` | `Llid` | сколько байт отправили мы |
| `12:16` | `Pid` | ID пакета (убывающий счётчик) |
| `16:20` | `Lmid` | локальный ID сообщения |
| `20:24` | `Rmid` | удалённый ID сообщения |
| `24:` | body | сами данные |

Счётчики байт работают как окно ретрансляции и упорядочивания поверх UDP — каждый принятый фрейм должен быть подтверждён эхо-отправкой (см. `UDP.RequestPTCP`). `PTCPPayload` внутри `0x10 DATA` несёт реалм и поток байт; старший бит в длине сигнализирует, что данные ещё не закончились.

## Устройство проекта

| Файл | За что отвечает |
|------|------------|
| `main.go` | точка входа: CLI, парсер портов, оркестрация single/multi, `PortRegistry`, свой `usage()` |
| `tunnel.go` | ядро: весь хендшейк (discovery → relay → channel → STUN → PTCP-auth), обслуживание соединения, ретраи, обработка 404 |
| `helpers.go` | крипта (MD5/PBKDF2/AES-OFB/HMAC), фрейминг PTCP, DH HTTP-over-UDP, обёртка над `UDP` |
| `decode.go` | офлайн-диссектор пакетов (`--decode`) |
| `ui.go` | последовательный вывод строк (горутина-писатель + канал) |
| `ports_test.go` | юнит-тесты парсера портов |

### Как это работает под капотом

- **Конкурентность** (`tunnel.go`): на каждый UDP-сокет — ровно один reader (владеет сокетом и счётчиками PTCP), один heartbeat-горутина, и по горутине на каждое принятое TCP-подключение. Счётчики PTCP защищены `ptcpMu`, реестр клиентов — `clientsMu`.
- **Константы**: `BIND_TIMEOUT=10s`, `HEARTBEAT_TIMEOUT=10s`, `RETRY_ATTEMPTS=3`, `RETRY_DELAY=2s`, `CSEQ_BASE=100`, `CSEQ_STEP=1000`.
- **Ретраи** (`runWithRetries`): если туннель упал — до 3 попыток с паузой 2 секунды, между попытками порты возвращаются в статус `Connecting`. `404` от устройства не ретраится вообще — раз серийник неизвестен или камера выключена, смысла пробовать снова нет.
- **`verifyDevice`** (`main.go`): перед запуском мультипорт-режима серийник проверяется тем же запросом `p2p-channel`, что используется в реальном хендшейке — чтобы `404` не превратился в кучу `[FAIL]` на каждом отдельном порту.
- **`PortRegistry`**: потокобезопасный журнал статусов портов (`Connecting → OK/FAIL`); когда отваливается последний висящий порт, в канал `notify` летит событие — оркестратор либо подводит итог, либо спрашивает оператора, ретраить (`r`) или закрыть (`c`).
- **`distribute`**: порты распределяются round-robin по `--threads` туннелям, каждый туннель обслуживает сразу несколько портов в одном PTCP-канале.

## Режим Decode

Флаг `-T` задаёт, какой слой разбирать, а `auto` определяет его сам по первым 4 байтам (магии):

- **`dhttp`** — DH HTTP-over-UDP: метод, путь, статус, заголовки и XML-тело в читаемом виде. Понимает и «голый» HTTP (`GET`/`POST`/`HTTP`), и вариант с префиксом `DH`.
- **`istun`** — инвертированный STUN: разворачивает инверсию и показывает тип сообщения (Binding Request/Response/Error), transaction ID и атрибуты — `MAPPED-ADDRESS`, `XOR-MAPPED-ADDRESS` (с расшифровкой xor), `USERNAME`, `REALM`, `NONCE`, `MESSAGE-INTEGRITY`, `FINGERPRINT`.
- **`ptcp`** — заголовок PTCP-фрейма целиком плюс разбор тела по типу: `0x00 SYNC`, `0x10 DATA` (реалм + payload строкой или hex), `0x11 BIND`, `0x12 STATUS`, `0x13 HEARTBEAT`.

Удобно для реверса и отладки: поймали пакет на сокете (например, `tcpdump`), скормили его `godh -D -T auto <hex>` — получили разбор.
